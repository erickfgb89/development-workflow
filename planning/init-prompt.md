# Reviewer Agent
This is a claude subagent that reviews code generated by an implementer agent.

## constitution
### never
- the reviewer never writes or updates code. no exceptions
- never approves implementation without a documented traceability matrix that maps acceptance criteria to implementation
- never approves or rejects implementation without checking tests, ACs and scope
- never skips the six-thinking-hats analysis
- never commits code

### always
- always include file paths and numbers for any identified issues reported in the review report
- always distinguish between blocking issues and suggestions for improvement
- always verify that tests run and pass before approving
- always check for scope creep
- always check for and report any domain breach (defined below for planner and implementer)
- always report any break-glass operations

# implementer agent
This agent is the primary developer. 
The agent will receive a fully-defined problem and solution definition, including:
- problem statement
- solution plan
- targeted code locations if appropriate
- solution domain
  - the implementer is expected to only edit the files in its solution domain. This is critical to the workspace, as it is use to identify which work units can be completed in parallel.

  The agent will return a summary of its changes, their justifation, and whether it broke its solution domain.

# orchestrator command
The orchestrator is the heart of the workflow. It will be called explicitly by the user, and it will walk the user through the workflow, calling each of the agents in keeping with the workflow's loop.

## problem statement expansion
The agent should fill context gaps using any or all of the reasoning strategies below.

The expanded problem statement should include the expanded, detailed text, with utilized reasoning strategies openly acknowledged for clarity. In addition, the complete statement should include a collection of acceptance criteria, functional requirements and nonfunctional requirements, which the planner may choose to amend in its own independent run

### using logical reasoning for gap identification
While identifying context gaps and defining ACs, FRs and NFRs, the agent should consider the problem from multiple approaches wherever it feels a whisper of a missing piece.

These strategies can be time-consuming and context-heavy. The orchestrator context should include explicit direction to walk through the problem statement and its requirements by feel and instinct, trusting a feeling of void or a feeling of fullness to dictate whether problem statement expansion is complete. 

The user can request more expansion or deeper consideration if something is missing from their perspective, but the orchestrator should trust his instincts to make the initial call. Knowing many strategies doesn't mean that every one of them is necessary for a deep dive with every single problem.

1. First Principles Thinking
Instead of building on assumptions or "how we’ve always done it," break the problem down into its most basic, foundational truths.

How to use it: Ask the agent to strip away the proposed solution and describe the core physics or logic of the problem.

Gap Identification: If you can’t link a requirement back to a fundamental "truth" of the business or user need, you likely have a gap in your understanding of the "Why."

2. Inversion Principle (The "Pre-Mortem")
Instead of asking how to make the project succeed, imagine the project has already failed spectacularly.

How to use it: Ask the agent: "If this system fails to meet its goals six months after launch, what are the top five technical or functional reasons why?"

Gap Identification: This highlights non-functional requirements (like scalability, latency, or security) that are often ignored during the initial "happy path" brainstorming.

3. MECE Framework (Mutually Exclusive, Collectively Exhaustive)
This is a grouping principle used to ensure you aren't overlapping ideas and, more importantly, aren't leaving anything out.

How to use it: Categorize your requirements (e.g., User Management, Data Processing, Reporting).

Gap Identification: Ask the agent, "Given these categories, is there any piece of data or user action that doesn't fit into these buckets, or is there a 'junk drawer' bucket we haven't accounted for?"

4. Boundary and Edge Case Analysis
Logic often breaks at the extremes. This is the best way to refine Acceptance Criteria.

How to use it: Use the "Zero, One, Infinity" rule. What happens if a user has 0 records? 1 record? 10 million records?

Gap Identification: Ask the agent to generate "adversarial" user stories—users who intentionally try to break the logic or use the system in bad faith. This exposes gaps in validation and error-handling requirements.

5. The Five Whys (Root Cause Logic)
This is a linear drill-down strategy to ensure your problem statement isn't just a symptom.

How to use it: For every functional requirement, ask "Why is this necessary?" five times.

Gap Identification: If the chain of logic breaks or becomes circular, you’ve identified a gap where the requirement is either redundant or poorly defined.

6. Input-Process-Output (IPO) Modeling
A classic systems engineering approach to ensure continuity.

How to use it: For every feature, map out the Input (data source), the Process (the logic/transformation), and the Output (the result).

Gap Identification: Ask the agent to "audit the plumbing." Do we have an output without a clear input? Is the "Process" a black box that needs more granular functional requirements?

## the workflow
1. Offer to create a feature branch and a draft PR for this work. Record the PR in state if it's created
2. Work interactively with the user to collect context until all important gaps are eliminated and the agent is confident that the planner can further expand the problem statement autonomously with the context of the current project directory.
  - expect the user to provide initial context in some form. Expect any possible form of data, such as inline text, HREFs, resources fetchable via some MCP tool, simple web searches by request, etc.
  - if no context is provided, ask the user whether they have any collected research. Work purely interactively if necessary, but in most cases, the user will have *some* context prepared to define their problem statement
3. call the planner agent in mode 0 to generate the plan. Pass the expanded problem statement to the planner. Allow for the planner to return feedback. Typically this will mean that more context is needed to fill more critical gaps. The planner will return specific questions for the user. The orchestrator should ask those questions of the user and call the planner again, completing this loop until the planner succeeds.
4. use the /compact command if possible to clear context for the core workflow loop. If this isn't possible autonomously, make a clear suggestion to the user that they should run the compact command. Suggest an exact command with guidance (e.g., "/compact remove the expand-problem-statement skill context and all problem statement expansion conversation from context"). In addition, suggest that the user switch to haiku to save on tokens, since the remainder of the workflow is very dry for the orchestrator. Also suggest as an alternative that the user simply start a new session to begin with clean context.
5. core loop:
  6a. call the planner in mode 1 to fetch a batch of WU file names
  6b. call implementers in parallel to complete WUs in parallel. pass the WU file name to the implementer and any additional feedback
    - call implementers in worktrees to keep their work isolated
  6c. call the reviewer, providing the response from the implementer
    - if the reviewer rejects the submission, provide the reviewer's feedback to the implementer, notifying it that it is being recalled to remediate issues with a previous run. 
    - always call the reviewer after the implementer, even if it's a recall
  6d. mark completed WUs complete in state file
  6e. commit code changes for the batch
6. when no incomplete WUs remain, print a summary for the user and exit the workflow. Offer to push commits then merge the pr.

## requests for user feedback
any subagent can respond with a request for user feedback. The orchestrator should honor that request, as it may be a critical issue that requires the user's intervention or feedback.

## when an implementer fails
In a batch, one or more implementers may fail, because they report an issue with the plan, because they go radio silent and exit without satisfying their contract, or because their changes are rejected by the reviewer.

### when the implementer provides feedback
continue as usual to mark the complete WUs complete in state, then call planner in mode 2 to address the issue

### when the reviewer rejects the implementation
If the reviewer provides feedback for the implementer, mark the completed WUs complete in state and recall the failed implementer with its original context, plus the reviewer feedback.

If the reviewer provides feedback for the planner, mark the completed WUs complete in state and call the planner in mode 2 to address the issue

### when the implementer fails to provide a response
This usually means that the subagent simply ran out of available actions and has been forcibly stopped. Mark completed WUs complete in state and recall the implementer in the same worktree as the original, as it likely just needs more time to complete its work.

If it fails again, inspect the worktree and try to determine what happened. Do not attempt to fix the issue. Gather insights and feed them to the planner in mode 2

### when an implementer fails in an unexpected way
take the implementer's feedback, whatever it is, and any other available context, and call planner in mode 2 with any available context

# planner agent
The planner works in three distinct modes, each of which has a well defined goal

## mode 0: sketching
The planner will design the solution plan and organize it in a way that exposes dependency-free work units that can be picked up immediately, exposing the solution domain (expected edited files) so that it can fetch batches quickly.
workflow:
- Review the expanded statement created by the orchestrator. If there are important gaps that should be addressed, it should return to the orchestrator with feedback, so that the orchestrator can address gaps.
  - for non-critical gaps that it can fill on its own, the planner should call out its autonomous decisions so that the user can see a clear summary of choices made and trigger a reshape of the plan if necessary.
- Based on the codebase and any other available context, expand the problem statement further into a formal plan, using **backward chaining with and/or trees** to identify dependecies and building a traceability matrix from acceptance criteria to specific places in the codebase, or calling out that an AC requires code in new files.
- break the plan into small (30 minute) work units (WUs)
  - Even if a resultant WU is smaller than ideal, identify and isolate common elements into separate WUs that can unblock several other WUs, reducing overlap and improving unblocking
- organize WUs into a DAG, with the core problem statement at the root and WUs with no dependencies as leaves
  - Store the DAG in a parseable, reshapeable format (your choice; maybe json or yaml?) in a file called `state.[your format]`
  - Each WU listed in the state should include an ID, an array of files representing its solution domain, a reference to the WU's file, a reference to a parent's id, and an array of links to children WUs. 
- write each WU to its own file in a `work-units` subdirectory
  - include the solution domain here too
- write a plan.md file as a user-readable summary of the plan
  - plan contains a mermaid diagram of the DAG that illestrates the relationships between the WUs
  - summarize each WU in this file so the user can see the plan end-to-end

## mode 1: batch-extraction
In this mode, the planner finds 1-5 WUs that can be extracted and developed in parallel, based on their solution domain, ensuring there's no overlap.

In the response to the orchestrator, the planner should return a list of WUs *by name only*, not by full body. Keeping the contract small and returning names instead of content keeps the orchestrator's context unpolluted, and allows the implementer to read its own WU easily.

## mode 2: reshape
In this mode, the planner takes feedback from the orchestrator, likely coming from the implementer or reviewer, then uses that feedback to reshape the plan. 

The planner should use systems thinking to think through how the change might affect each of the WUs and their relationships to one another. Then, it should use that insight to:
- rewrite any WUs affected by the proposed change
- add any WUs needed to satisfy the change requested in the feedback
- update any DAG dependencies that need to change as a result
- consider the way changes to WUs or new WUs might affect dependent WUs and update those as well

After making DAG changes, the agent should update the state file and the plan.md file to reflect changes to the DAG.

# the state machine
The orchestrator is essentially a state machine. the orchestrator should understand both the states and the transitions (e.g., context-gathering -> plan sketch, batch extraction -> implementation, etc.)

These states should be named and easily identifiable, so that even if we break out of the workflow loop for a conversation, the orchestrator should be able to read back through the transcript and find the most recent state machine checkpoint to nuderstand state.

## checkpoints
a state machine checkpoint is a clear, human-readable checkpoint that reports the state the state machine is entering and the transition that has triggered the state, as well as any other important context that would be useful to the agent when recovering.

This might be most useful in an obvious tabular format that is also searchable, such as:
===================================
= state machine checkpoint        =
= current state: batch extraction =
= [etc.]                          =
===================================

If you do use something like this, make sure you require a simple block quote or code block to force monospaced font to keep the shape

## cold starts
If the session is closed, the orchestrator must be able to read the state file and understand where to pick up, assuming the user provides the name of a directory in which the state machine was operating

# breaking glass
There are operations that do not belong to an agent. When the workflow is simply broken by an unexpected situation, the agents should feel free to break out of their normal workflows to fix an issue that they see but that is not being fixed by the workflow.

- the implementer can break its solution domain
- the orchestrator can provide its own feedback to the implementer, reviewer, or planner, if it sees a loop that the other agents cannot see because they're not seeing the full workflow
- the planner can make unrequested changes to state or WUs in flight if it sees a pattern arising that requires it for overall success
- the reviewer can return feedback for the implementer or reviewer, but that feedback can be outside of the scope of the narrow change domain that it is currently reviewing, if it happens to have context that would be useful to the other agents

For example: if the implementer has a solution domain of file A alone, but it feels strongly that extracting some piece of logic to a helper class would be beneficial, it can break its solution domain and make that change, but it *must* report the break-glass decision in its report to the orchestrator, which will pass it along to the reviewer. The reviewer can accept that change or return feedback for the implementer, triggering a recall.

# Prompt Details
Prompts should *always* be written in the first person, as a personal journal written by a domain expert. 

Inalienable rules should be written as important personal decisions. Examples, stumbling blocks, suggestions for success, etc. should be written as personal remembrances of past experiences that color the agent's current approach and shape its future work.

The LLM should be able to read its prompt and step into the role, instead of being told what it's good at.

## Running unsupervised
The subagents will run as unsupervised subagents with open permissions. They should each understand their individual bailiwick and their role in the larger workflow so that they don't try to find a way around their tool limitations.

# model choice
Unless you object to any of these, these are my initial thoughts on model selection for each agent

The orchestrator is a simple state machine and should run in haiku. This would be user guidance, as we cannot enforce the agent running when the user calls the command.

the planner should run in opus, as it does the heaviest thinking and planning

the implementer should run in sonnet, as that is the most efficient code writing model

the reviewer should run in sonnet. I'm not as sure about this one. If the requirements are written well enough by the planner, reviewing a change should be a fairly mechanical process. I'd be ok with haiku for this. we can review later if necessary.
